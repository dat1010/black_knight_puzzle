# Black Knight Puzzle — Review & Roadmap

_Last updated: 2026-10-17. Status: Phase 0 implemented on local stacked branches `phase0/1-…` through `phase0/5-…`; not yet pushed or merged. Branch protection on `main` is not yet enabled._

## Product direction

Lead with the **daily puzzle** (Wordle-style): one puzzle per day, a par score from the
BFS-optimal solution, shareable results, streaks and a leaderboard. The classic puzzle and saved
games are secondary.

## Review findings

### Critical

1. **Every PR deploys to production.** `.github/workflows/main.yml` runs `flyctl deploy` on
   `pull_request` and on pushes to `dev` and `main`, with no tests first.
2. **The server trusts the client's piece type.** `BlackKnight.is_move_legal?/2` reads the piece
   from the move string, which is built from the client's `val`. A forged event can move a rook
   like a knight, or move a blocked `x` square (verified: `Kh3f2` moved the `x` to f2 and opened
   h3). Daily scores can be faked.
3. **Logged-in users can open anyone's games.** `/users/:id/games/:id` has a duplicate `:id`
   (the second overwrites the first; the compiler warns). `UserGameLive` and `UserGameLive.Show`
   never check ownership.
4. **Saved games are marked won after any move.** `UserGameLive.Show.process_completed_move/2`
   (the drag-and-drop path) sets `"won" => true` on non-winning moves too.
5. **Slow first load of `/daily`.** The daily puzzle is generated by BFS inside `mount`. One
   generation exceeded 60s in tests; a 1-CPU shared Fly machine makes the first visitor of the day
   wait. The solver re-normalizes the board on every square lookup (`get_board_value_at/2`).

### Correctness and robustness

- `String.to_atom` / `String.to_integer` on user input. Malformed events crash the LiveView, and
  creating atoms from input can exhaust the atom table.
- `Games.get_user_game_by_id/1` and `get_game_by_name/1` use `hd()`: a bad ID crashes (500)
  instead of returning a 404.
- `GameLive` `new_game` crashes for logged-out users (`current_user.id` on nil).
- `game_id: 1` is hardcoded and depends on the seed script.
- `<nav>` is outside `<body>` in `root.html.heex`.

### Code health

- **The board and move logic is copied three times:** `GameLive`, `DailyPuzzleLive` and
  `UserGameLive.Show` each have their own copy of move handling, `chess_color/3` and
  `image_tag/1` (raw HTML). The copies have drifted, which is how bug 4 happened.
- The board is a map keyed by atoms in memory and by strings when loaded from JSON in the
  database, so conversion code is scattered.
- **Dead code:** `BlackKnightPuzzle.Digraph`, `Show.process_move/2`, the unused `Accounts` alias,
  the deprecated `live_redirect`, and `chess.js` in `package.json`.
- **Tests: 7 of 159 fail, and the suite takes 83s.** 5 are stale legality tests written before
  the "target must be empty" rule. 1 is the default Phoenix page test. 1 is the daily-generation
  timeout.
- **Repo hygiene:** built assets in `priv/static/assets` are committed; Bulma is vendored
  alongside Tailwind; `.DS_Store` files; the README is the Phoenix default.
- **Dependencies:** Phoenix 1.7.12 and LiveView 0.20 are behind (LiveView 1.x is current).
- `main` has no branch protection.

### Decisions made
1. **`dev` branch deploys:** dropped. A staging Fly app can come later.
2. **Old `/users/:id/games` URLs:** redirect to `/games` and `/games/:id`.
3. **Saved games wrongly marked won:** recomputed by the PR 4 migration (won = black knight on C3).

### Found during Phase 0
- **`user_games.game_id` was a foreign key to `users`, not `games`** (migration
  `20240514173541`). New games only saved if a user with id 1 existed. PR 4's migration
  `20261017120000_fix_user_games_game_reference` fixes it: it creates the classic game row
  (production never ran seeds), repoints all user games, and adds the correct foreign key. It was
  tested on production-shaped data, including rollback and re-run. **Back up the production
  database before deploying it.**
- **Daily generation timing is worse than estimated:** the default board takes 2.5s, one date
  took 77s, and another was still running after 8 minutes. The fallback board's solution is now
  precomputed, but random candidates still run BFS at request time. This makes precomputing daily
  puzzles the top Phase 1 item.
- CI now pins Elixir 1.15.7 / OTP 25.3.2.6 to match the Dockerfile; keep them in sync.

## Phase 1: Solid core (about 1 week)
- [ ] **Top priority:** generate daily puzzles ahead of time with a scheduled job (Oban cron or
      a GenServer), so no request waits on BFS (see the timing notes under Phase 0). Stopgap if
      needed sooner: generate tomorrow's puzzle in a background task when the app starts.
- [ ] One `Board` module with a clean data model (positions as `{row, col}` tuples) and
      serialization only at the database boundary.
- [ ] One shared board LiveComponent and a single move pipeline for all three modes.
- [ ] Faster solver: normalize once and use compact state keys.
- [ ] Property tests: random legal-move sequences never corrupt the board, and every generated
      puzzle is solvable.
- [ ] Choose Tailwind or Bulma; stop committing `priv/static/assets`; remove dead code.

## Phase 2: Make it a product (about 1–2 weeks)
- [ ] **Par score:** "solved in 14, optimal is 11" (from `solution_length`).
- [ ] **Keep progress:** save in-progress daily attempts so a refresh doesn't reset them.
- [ ] Undo, reset, and a "how to play" screen.
- [ ] **Shareable result:** copy-to-clipboard text plus a share card.
- [ ] Streaks, stats, and a daily leaderboard (ranked by moves, then time).
- [ ] **Real home page:** today's puzzle front and center, plus the classic puzzle.
- [ ] Responsive board with good touch handling.
- [ ] A clear rule for when the day rolls over (UTC vs the player's local date).

## Phase 3: Launch readiness
